# ADR 003 — Librairie de composants d'interface

## Statut

Accepté — 10/09/2026

## Contexte

Le lot 1 exige un formulaire complet (messages par champ, soumission désactivée pendant l'envoi), quatre états sur chaque écran de données, une confirmation de suppression et une barre d'annulation. Écrits à la main, ces éléments demandent une dizaine de primitives — bouton, champ, bascule, étiquette, dialogue, barre temporaire, jauge — chacune avec ses sept états (repos, survol, focus, appui, désactivé, chargement, erreur).

Trois contraintes pèsent sur ce choix. La cible n°1 est le **navigateur** via `react-native-web` : la librairie doit y être solide, pas seulement sur mobile. Le critère éliminatoire du **fichier de plus de 250 lignes** interdit les solutions qui copient leurs composants dans le dépôt. Et la recette juge la cohérence : un bouton qui ne ressemble pas au bouton d'à côté est une faute.

## Options envisagées

1. **Primitives maison** (état initial du lot). Contrôle total et zéro dépendance, mais chaque état d'interaction est à écrire et à tester ; l'accessibilité (`aria-invalid`, régions vivantes, noms accessibles) se réimplémente à chaque composant, et une omission ne se voit pas.
2. **gluestack-ui v2 + NativeWind.** Les composants sont copiés dans le dépôt, donc modifiables — mais ils comptent alors dans nos fichiers, et la configuration touche Babel, Metro et Tailwind.
3. **Tamagui.** Compilateur d'extraction de styles, thèmes puissants. Le gain de performance ne se voit pas sur une liste de vingt lignes, et le surcoût de configuration est immédiat.
4. **React Native Paper.** Material 3, mature, éprouvé sur `react-native-web`. Couvre exactement les besoins du lot : `TextInput` avec `error` et `HelperText`, `Button` avec `loading`/`disabled`, `Dialog`, `Snackbar` avec action, `List.Item`, `Chip`, `ProgressBar`, `Banner`. Une dépendance, aucune configuration de build.

## Décision

Nous retenons React Native Paper.

La palette du projet n'est pas abandonnée : `theme/paper.ts` traduit nos jetons dans le vocabulaire Material 3 (`primary`, `errorContainer`, `outlineVariant`, niveaux d'élévation neutralisés) et ce thème est le **seul** point de contact entre la palette et la librairie. Aucun composant ne lit `couleurs.*` pour styliser un élément que Paper sait styliser.

L'échelle typographique maison a été supprimée au profit de celle de Paper (`variant="headlineSmall"`, `bodyMedium`, `labelMedium`), avec la police système injectée via `configureFonts`. Le seul thème déclaré est le thème clair, conformément à la scène d'usage décrite dans `PRODUCT.md`.

Deux composants restent à nous, faute d'équivalent :

- `Squelette` / `SqueletteListe` / `SqueletteFiche` — Paper n'offre pas de squelette, et le sujet exige « un squelette, pas un spinner plein écran ». Les nôtres reprennent la forme exacte du contenu attendu.
- `Couverture` — la résolution des trois formes d'URL de couverture est une règle métier, pas un composant d'interface.

## Conséquences

**Positives** : les états d'interaction, les noms accessibles et les régions vivantes viennent de la librairie et sont testés en amont ; la `Snackbar` porte nativement le couple message + action de l'annulation ; le vocabulaire visuel est cohérent d'un écran à l'autre sans discipline particulière ; environ 400 lignes de primitives maison ont disparu du dépôt.

**Négatives assumées** : le poids du bundle web passe de 1,75 Mo à 2,31 Mo — c'est la contrepartie directe, à surveiller dans `docs/PERFORMANCE.md`. L'apparence est reconnaissable comme Material : le thème l'éloigne du Material par défaut (coins peu arrondis, élévations neutralisées, accent encre) sans le nier. Enfin, deux pièges propres à `react-native-web` ont dû être traités et sont commentés dans le code : `ProgressBar` occupe toute la hauteur de son parent, et le glyphe d'une icône entre dans le nom accessible d'un `Button` si aucun `accessibilityLabel` ne le fixe.
