# ADR 001 — Gestion de l'état serveur

## Statut

Accepté — 09/09/2026

## Contexte

Le lot 1 impose l'affichage, l'ajout, la modification et la suppression d'ouvrages, avec pagination côté serveur, quatre états d'écran obligatoires (chargement, erreur, vide, succès) et une invalidation propre après chaque mutation. L'API impose une pagination stricte (`GET /books?page=&limit=&q=&status=&favori=&sort=&order=`) et le cahier des charges interdit de charger les 500 ouvrages pour filtrer côté client.

Le lot 4, prévu plus tard, ajoutera une file de mutations hors ligne et une synchronisation par lot. La solution retenue ici doit rester compatible avec cette évolution sans réécriture de la couche données.

Contraintes : réseau instable (latence, échecs en mode chaos), interdiction de logique métier ou d'appel réseau dans `app/` et `components/`, nécessité de clés de cache structurées par page/filtre/tri.

## Options envisagées

1. **State management manuel** (`useState` / `useReducer` + `fetch` dans des hooks maison) : contrôle total, mais réimplémente à la main le cache, la déduplication de requêtes, les états de chargement et l'invalidation — risque élevé de bugs et de code dupliqué sur chaque écran de données.
2. **Redux Toolkit + RTK Query** : solution robuste, mais charge conceptuelle et volume de code disproportionnés pour la taille du projet ; recouvre des besoins (état global applicatif) que le sujet ne demande pas.
3. **TanStack Query** : bibliothèque dédiée à l'état serveur (cache, revalidation, déduplication, retries, invalidation ciblée), clés de requête structurées naturellement adaptées à la pagination et aux filtres, intégration directe avec les quatre états d'écran demandés.

## Décision

Nous retenons l'option 3, TanStack Query, pour toute donnée provenant de l'API.

Les clés de cache sont **hiérarchiques**, produites par une fabrique unique (`services/queryKeys.ts`) et jamais écrites à la main dans un hook :

```
['books']                          racine
['books', 'list']                  toutes les listes
['books', 'list', { …filtres… }]   une liste précise
['books', 'detail']                toutes les fiches
['books', 'detail', id]            une fiche
```

Trois conséquences de cette forme :

- **La page n'entre pas dans la clé.** Avec `useInfiniteQuery`, elle est le `pageParam` : l'y laisser ferait de chaque page une entrée indépendante et empêcherait le défilement infini attendu au lot 2.
- **Les filtres sont normalisés avant d'entrer dans la clé** (`normalizeFilters`, dans `domain/`). Sans cette étape, `{}` et `{ sort: 'titre', order: 'asc' }` désignent la même réponse serveur mais occupent deux entrées de cache, donc deux requêtes réseau pour rien.
- **L'invalidation est ciblée.** Un niveau `'list'` distinct de `'detail'` permet de périmer toutes les listes sans toucher aux fiches déjà chargées — ce qu'une clé plate ne permet pas.

Chaque mutation invalide `['books', 'list']` dans son intégralité : c'est le serveur qui trie et pagine, donc rien ne permet de prédire sous quels filtres ni sur quelle page un ouvrage modifié atterrira. En revanche, la fiche renvoyée par le serveur après une écriture est écrite directement dans le cache via `setQueryData` plutôt que redemandée — on utilise ce que le serveur a donné, on invalide ce qu'on ne peut pas recalculer.

Le client HTTP sous-jacent (URL de base, en-têtes, délais d'expiration, mapping des erreurs) reste isolé dans `services/api/`, appelé uniquement par les hooks de `features/books/`. Aucun composant n'accède directement à `fetch` ou à une URL en dur.

## Conséquences

**Positives** : cache et invalidation gérés par la bibliothèque plutôt qu'à la main ; gestion native des états `isLoading` / `isError` / `isSuccess` correspondant aux quatre états d'écran exigés ; réduction du code répété sur chaque écran de données ; base compatible avec l'ajout ultérieur d'un cache persistant (lot 4, via un persister TanStack Query) sans changer l'architecture des hooks.
