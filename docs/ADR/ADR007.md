# ADR 007 — Mode hors ligne, file de mutations et idempotence

## Statut

Accepté — 11/09/2026

## Contexte

Le lot 4.2 exige qu'un libraire en réserve, sans réseau, voie son fonds, puisse ajouter,
corriger et supprimer un ouvrage, écrire une note, et que tout cela reparte au retour du
réseau **via `POST /sync`**, dans l'ordre, sans doublon. Le sujet demande explicitement de
traiter le cas où **le jeton d'accès expire pendant la synchronisation d'un lot**, et que la
fonction qui décide du sort d'une mutation face à une réponse serveur soit **pure et testée**.

L'API mémorise le résultat de chaque mutation par son `id` client et le renvoie avec
`rejeu: true` si le même `id` revient : c'est elle qui garantit l'absence de doublon, à
condition que le client **génère l'`id` une fois et le conserve** entre deux tentatives. Les
notes, elles, n'ont pas d'identifiant client : `POST /books/:id/notes` n'est pas idempotent.

L'évaluation se déroule en mode chaos (1,5 s de latence, 30 % de 503), ce qui rend les
échecs partiels d'un lot ordinaires, pas exceptionnels.

## Question 1 — Un chemin d'écriture ou deux ?

### Options envisagées

1. **Deux chemins** : en ligne, appeler directement `POST /books`, `PUT`, `PATCH`, `DELETE` ;
   hors ligne, mettre en file et rejouer via `/sync`.
2. **Un seul chemin** : toute écriture est mise en file, appliquée au cache immédiatement, et
   la file est synchronisée aussitôt si le réseau est là.

### Décision

**Un seul chemin.** Deux chemins signifient deux codes à tester, deux façons d'écrire le cache
et une bascule « suis-je en ligne ? » qui se trompe précisément quand le réseau vacille. Avec
un seul chemin, un 503 du mode chaos sur une création n'est plus un cas particulier : la
mutation reste en file avec son `id`, repart plus tard, et le serveur la reconnaît. La
fonction `decider` et la fusion de file servent en ligne comme hors ligne.

Le coût est une latence perçue nulle mais une confirmation serveur différée : la fiche
apparaît avec un identifiant `local:` et `version: 0` jusqu'à ce que le serveur la nomme. Une
table d'alias (`services/sync/alias.ts`) fait suivre l'identifiant réel aux écrans déjà
ouverts sur l'identifiant local.

## Question 2 — Où vit la file ?

### Options envisagées

1. Les **mutations en pause de TanStack Query** (`networkMode: 'offlineFirst'`, cache de
   mutations persisté, `resumePausedMutations`).
2. Un **store maison** persisté via `services/storage`, lu par `useSyncExternalStore`.

### Décision

**Store maison** (`services/sync/file.ts`). TanStack rejoue requête par requête, sans lot
`/sync`, sans fusion de deux modifications du même ouvrage, et la logique de décision se
retrouverait éparpillée dans les `onError` de chaque hook. La file est un simple tableau JSON
validé par zod à la lecture : une valeur corrompue rend une file vide plutôt qu'une
application qui ne démarre plus.

Chaque ajout passe par `fusionnerFile` (pur) : deux corrections du même ouvrage deviennent
une seule ligne, une création suivie d'une suppression disparaît avec ses notes. Une mutation
déjà partie dans un lot (« en vol ») n'est jamais fusionnée : ce qui est sur le fil reste tel
quel jusqu'à la réponse.

TanStack est réglé sur `networkMode: "always"` pour les requêtes et les mutations : hors
ligne, une lecture doit **échouer** pour que l'écran retombe sur le cache et le dise, et une
écriture doit **partir dans la file** quoi qu'en pense le navigateur.

## Question 3 — Que se passe-t-il si le jeton expire pendant un lot ?

Le lot est envoyé par `services/api/sync.ts`, donc par `client.ts`, donc par
**l'intercepteur unique** de l'ADR 006. Un 401 `jeton_expire` sur `/sync` déclenche le
rafraîchissement (à vol unique) puis le rejeu **du même corps, avec les mêmes `id`**. Le
serveur, qui avait déjà appliqué tout ou partie du lot avant de répondre, renvoie
`rejeu: true` pour ce qu'il connaît : `decider` traite un rejeu exactement comme une première
réponse. Aucune création n'est doublée, aucune n'est perdue.

Si le rafraîchissement lui-même est refusé, `surSessionPerdue` déconnecte le libraire ; la
file, les conflits et les alias **restent sur disque**. Ils ne sont pas effacés à la
déconnexion — volontaire ou non — parce qu'ils appartiennent au poste, pas à la session : la
prochaine connexion sur ce poste relance la synchronisation. Une déconnexion volontaire avec
des modifications en attente demande confirmation et le dit en toutes lettres.

## Question 4 — Et les notes ?

`/sync` ne connaît pas les notes. Elles sont mises en file comme le reste, mais rejouées
après les livres, une par une, sur `POST /books/:id/notes`, une fois que leur ouvrage a un
identifiant réel. Faute d'identifiant client, la déduplication se fait par le contenu : les
notes existantes sont lues avant l'envoi, et un texte identique déjà présent est pris pour
« déjà enregistrée ». C'est une approximation assumée : deux notes strictement identiques sur
le même ouvrage n'ont pas de sens métier.

## Question 5 — Comment savoir que l'on est hors ligne ?

Sans dépendance. Sur le navigateur, `navigator.onLine` et les événements `online` /
`offline` ; partout, le **résultat des requêtes** : une requête qui n'atteint pas le serveur
bascule « hors ligne », la première réponse — quel que soit son statut — rebascule. Un 503 n'est
pas « hors ligne » : le serveur a répondu, il souffre. Sur natif, l'application démarre en
ligne et se corrige dès la première requête.

## Question 6 — Le cache

`@tanstack/react-query-persist-client` sur `services/storage`, sept jours, invalidé par la
version de l'application (`buster`). Les réponses d'Open Library sont exclues (commodité, pas
donnée du libraire) ainsi que toute requête en erreur. Au démarrage, la file est **réappliquée
au cache** (`rejouerLocalement`) avant la première synchronisation : le cache et la file sont
écrits à deux moments, et un rechargement dans les 300 ms qui suivent une note pourrait
trouver la note dans la file et pas encore dans le cache. La file est la vérité sur ce que le
libraire voulait.

Après une synchronisation, les listes sont marquées périmées mais **pas rechargées** (règle de
l'ADR 005 : ne pas déplacer la ligne sous le doigt) ; les fiches ouvertes le sont dès que la
file est vide, ce qui ramène aussi leurs notes serveur.

## Conséquences

- `services/sync/decision.ts`, `mutation.ts`, `fusion.ts` n'importent ni store, ni réseau, ni
  horloge : ce sont les seuls endroits où une règle de synchronisation s'écrit, et ils sont
  testés ligne à ligne, cas de conflit compris.
- Un ouvrage créé hors ligne a un identifiant `local:` visible dans l'URL jusqu'à la
  synchronisation. Les écrans passent par `useIdReel` et continuent de fonctionner quand
  l'identifiant réel arrive.
- Les hooks d'écriture ne connaissent plus d'erreur réseau : la file est locale. Ce qui peut
  être refusé l'est plus tard, et arrive dans le store des conflits (ADR 008).
- Limite connue : un filtre jamais consulté en ligne n'a rien en cache et affiche l'écran
  d'erreur hors ligne. Le serveur filtre ; l'application ne refait pas ce travail.
